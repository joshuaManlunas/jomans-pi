Orca Meshed Agents

A quick guide to standing up a team in Orca.

Your current Orca terminal is the orchestrator and owns one orchestration Run. Add an optional advisory Oracle and N workers, each its own supervised worker on that Run, started with orca orchestration worker-start. Every member can message every other member directly through orca orchestration send: members at dispatch:<id>, the orchestrator at run:<id>.

Orca only, not Herdr. Orchestration must be enabled in Orca Settings → Experimental. The team reads its role prompts from this skill directory by default.

Choose the team

Invocation flags; worker count excludes you and the Oracle.
FlagDefaultUse
--workers N4Positive worker count.
--worker-model agent[:model][,agent[:model]...]codex:gpt-6.1-solOne selection for all workers, or exactly N selections in worker order. A bare agent uses its configured default model.
--worker-effort L[,L...]UnsetLaunch effort for workers; needs an explicit model.
--oracle agent[:model]codex:gpt-6-astraChoose the Oracle independently.
--oracle-effort LUnsetLaunch effort for the Oracle; needs an explicit model.
--no-oracleUnsetOmit the Oracle; mutually exclusive with --oracle and --oracle-effort.
--prompts-dir DIRThis skill directoryExisting orchestrator.md, workers.md, and, with Oracle, oracle.md.

A selection is an Orca agent id (claude, codex, cursor, antigravity, muse, opencode, …) and an opaque provider model ID, split at the first colon. Orca has no model listing; it validates agent, model, and effort at launch, and the agent stops rather than substituting when a start is refused or launch.effective differs.

Sample usages

Use the / line in Claude Code or the $ line in Codex. Enter one line as an agent prompt in an Orca terminal, not as a shell command.

Default: four Codex workers and a Codex Oracle

/orca-meshed-agents
$orca-meshed-agents

Two mixed workers and a Codex Oracle

/orca-meshed-agents --workers 2 --worker-model codex:gpt-6.1-sol,claude:claude-sonnet-5-5 --oracle codex:gpt-6-astra
$orca-meshed-agents --workers 2 --worker-model codex:gpt-6.1-sol,claude:claude-sonnet-5-5 --oracle codex:gpt-6-astra

Three workers without an Oracle

/orca-meshed-agents --workers 3 --no-oracle
$orca-meshed-agents --workers 3 --no-oracle

All-Claude workers and Oracle, Oracle at high effort

/orca-meshed-agents --workers 3 --worker-model claude:claude-sonnet-5-5 --oracle claude:claude-opus-5-5 --oracle-effort high
$orca-meshed-agents --workers 3 --worker-model claude:claude-sonnet-5-5 --oracle claude:claude-opus-5-5 --oracle-effort high

Maximum: twenty workers, no Oracle

/orca-meshed-agents --workers 20 --no-oracle
$orca-meshed-agents --workers 20 --no-oracle

At most 20 workers. With an Oracle, the maximum is 19 workers. Your current orchestrator terminal is additional and keeps its model, including in the all-Claude example.

What standup looks like

Run → plan → worker-start → BOOT_ACK → pairs → matrix → READY. Each member's tab is renamed <squad> -- <Name> (Worker) or <squad> -- Oracle (Orca otherwise shows worker-<taskId>). Members load their roles, prove direct PING/ACK communication for every pair, then acknowledge READY. Work starts only after a later assignment. With n total members, verification covers n(n−1)/2 pairs.

The helper lives beside SKILL.md. With Node.js ≥18, set ORCA_MESH_SKILL_DIR to this skill directory; run data lives in .orca-mesh/ at the workspace root (self-ignored by git) unless ORCA_MESH_ROOT overrides it. These are helper commands for the agent, not replacements for the skill:

plan — write the plan and standby files, and print one worker-start command per member.
node "$ORCA_MESH_SKILL_DIR/orca-mesh.mjs" plan --orca-run "$ORCA_RUN_ID" --orca-cli orca
bootstrap — validate the saved worker-start receipts and generate roles, roster, tab renames, and send commands.
node "$ORCA_MESH_SKILL_DIR/orca-mesh.mjs" bootstrap --run "$ORCA_MESH_RUN"
resend — print a deliberate repeat of one member's protocol message with a fresh retry ID (re-running a saved command only replays it).
node "$ORCA_MESH_SKILL_DIR/orca-mesh.mjs" resend --run "$ORCA_MESH_RUN" --name leia --kind go --round 1
matrix — verify recorded pair reports and write the pair matrix.
node "$ORCA_MESH_SKILL_DIR/orca-mesh.mjs" matrix --run "$ORCA_MESH_RUN"
selftest — test the helper without launching workers.
node "$ORCA_MESH_SKILL_DIR/orca-mesh.mjs" selftest

The agent binds the Run with orca orchestration run-create, retains run/directory values from plan, and saves each worker-start JSON receipt to the save path in its entry (start-<name>.json). Every mutation carries a stable --retry-request so retries replay instead of duplicating.

After READY

Assign work to the squad

Use the ready squad to implement the requested change. Assign disjoint files, give each worker acceptance criteria and checks, then review and integrate their results.

Consult the Oracle

Ask the Oracle to critique this implementation plan before we edit. Send the task context and constraints, wait for its result, then decide how to proceed.

Run a task at higher effort

Leia's last attempt was shallow. Start a separate supervised worker for that task with the same model as Leia and a higher --effort, then review its result.

Disband the squad

Disband the squad: have every member send worker_done, then release each worker.

Roles are loaded conversationally, not injected as system prompts. Members share your workspace, branch, and checkout, so give them separate file ownership. Orca sets effort only at launch, so a running member's effort cannot be raised in place. Member Dispatches stay active while idle and settle only at disband.
